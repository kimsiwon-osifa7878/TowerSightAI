# CONTEXT — 차량 직육면체 검증: 왜, 무엇을, 어디까지 (2026-09-16)

이 문서는 `vehicle_box_test/` 랩의 **배경·의도·판단 근거·검증 결과**를 남깁니다.
새 세션이 이전 대화 없이도 같은 맥락에서 이어받게 하는 것이 목적입니다.
코드 사용법은 [README.md](README.md), 설계 확정안 원본은 저장소 루트 `INTENT.md` §4입니다.

---

## 1. 왜 이걸 하는가

현재 주차 프로세스 엔진의 **2단계(정렬) 판정은 임시 휴리스틱**입니다.
`towersightai/process/engine.py`의 `_front_vehicle_stable()` — 전면 카메라 Hailo bbox 중심이
`motion_epsilon_norm`(0.03) 안에서 `stop_stable_seconds`(5초) 이상 안 움직이면 "정차"로 봅니다.
여기에 전면 사다리꼴 바퀴 유도선을 얹어 운전자가 눈으로 맞추는 방식입니다.

이 방식은 **"차가 주차기 안에 제대로 들어왔는가"에 답하지 못합니다.** 필요한 것은 차량의
실제 길이·폭·높이와 팔레트 기준 위치·회전각이고, 그 수단으로 **카메라 외곽선 → 3차원
직육면체 추정**이 2026-09-09 문답으로 확정됐습니다 (INTENT.md §4).

용도는 세 가지입니다: ① 정렬 안내(좌우/전후) ② 정차 위치 판정(허용 범위) ③ 차량 크기 제한 검사.
결과는 안전 게이트의 **입력**일 뿐이며, 불확실하면 WAIT/NG입니다.

## 2. 사용자가 이번에 지시한 것 (2026-09-16)

원문 요지:

1. **테스트용 코드를 별도 폴더로 분리**할 것. 거기서 먼저 작업하고, **가설이 검증되면**
   그 후에 주차기 앱을 업데이트한다.
2. 첫 할 일은 **NAS에서 차량이 들어있는 스크린샷·동영상을 표본 추출해 다운로드**할 것.
   **차량 전체가 안 들어와도 된다 — 일부만 있어도 어느 정도 되는지를 봐야 한다.**
   동영상은 몇 프레임 단위로 잘라 쓰면 된다.
3. **체커보드로 왜곡 보정은 안 했지만**, 현장 카메라 위치는 고정이고 **주차기 내부 바닥의
   원판 크기가 신안타워 설계도에 있으니 그것으로 보정해서 크기를 잡으라.**
4. 설계한 대로 차량 위치를 가늠해 **직육면체를 그리거나**, 최소한 **차량 앞·뒤·바퀴 양옆을
   특정**할 수 있다면 사용한 이미지에 **선을 그어** 직접 판단할 수 있게 하라.
5. 그렇게 만든 이미지들을 정리해 **사람이 보고 검증할 수 있는 HTML**로 만들라.
6. **특정하지 못한 이미지(차량이 있는데도)는 왜 안 됐는지를 이미지 안에 한국어로 메모**해
   저장하라. 즉 **이미지만 보고 파악할 수 있게** 만들라.
7. 직육면체나 앞뒤 위치가 파악됐으면 **길이 같은 치수도 이미지에 표시**하라.

→ 이 폴더의 설계 규칙은 전부 여기서 나옵니다. 특히 6번(실패 사유를 이미지에 새긴다)은
이 랩의 출력 형식을 결정한 요구사항입니다.

## 3. 이번에 실제로 한 일

### 3.1 NAS 표본 수집

- `data/analysis/sites.json`의 현장 설정으로 SFTP 접속(analyze 대시보드와 같은 strict host key 정책), **읽기 전용**.
- `raw/<host>/<day>/`의 **이벤트 샤드만 먼저** 받아서 읽고, 두 가지를 뽑았습니다.
  - `media_artifact_created` → 미디어 목록(경로·SHA-256·크기·카메라·시각·종류)
  - `detection_batch` → 차량 라벨(car/truck/bus/motorcycle) 검출의 카메라별 시각
  - `vehicle_entered` / `vehicle_session_ended` → **입고 세션 구간**
- 미디어마다 "그 시각 그 카메라에 차량이 몇 번 잡혔는가"로 점수를 매겨,
  차량/번호판 이벤트 → 입고 세션 구간의 사람 이벤트 → 차량 검출이 겹치는 것 순으로
  날짜·카메라를 고르게 섞어 표본을 뽑았습니다.
  (입고 세션 단위로 뽑으면 **같은 시각 3개 카메라 자료**가 함께 들어와 교차 검증에 좋습니다.)
- 결과: 17일치 스캔 → **276건 선정, 272건 다운로드**(4건은 샤드에 기록됐으나 NAS에 없음).
  클립 15개에서 **프레임 323장** 추출.

수집 중에 고친 현장 데이터의 실제 문제:
- `.jsonl` 확장자인데 내용은 gzip인 샤드가 있어 **확장자 대신 매직바이트로 판별**.
- **잘린 gzip 샤드**가 있어 읽은 데까지만 쓰고 넘어가도록 방어.
- `raw/<day>` 레거시 레이아웃과 `raw/<host>/<day>`가 공존 → (호스트, 날짜)로 병합.

### 3.2 지면 교정 — 원판과 레일로

체커보드 내부 파라미터가 없으므로, **바닥에 실제로 있는 실치수 물체**로 지면↔영상
호모그래피를 직접 맞췄습니다. 현장 영상에 항상 보이는 것:

- **턴테이블 원판** Ø6,100 mm (승인도 J002)
- **노란 레일** 두 줄, 팔레트 폭 2,200 / 레일 내폭 2,106 mm (승인도 J001)

카메라별로 방법이 달랐습니다.

| 카메라 | 방법 | 결과 |
|---|---|---|
| `opposite_side` | 확대 이미지에서 **팔레트 데크 네 모서리**를 눈으로 읽음 | 투영한 레일·팔레트가 실물과 일치. 투영한 원판은 화면 주변부에서 어긋남(어안 왜곡) |
| `front` | 노란 레일의 **인터로킹 매트 톱니 26개**로 x 축척 | 재투영 오차 평균 13 mm / 최대 48 mm |
| `rear_side` | 미교정 | 이 화각에서 팔레트 네 모서리를 아직 못 읽음 |

**톱니 간격 114.8 mm는 opposite_side 교정에서 역산한 값**입니다. 전면 카메라는 알려진 x
기준이 팔레트 끝 하나뿐이라 축척이 결정되지 않는데, 같은 매트의 톱니 주기를 이미 교정된
카메라에서 재서 가져오는 방식으로 풀었습니다. (자기상관으로 주기를 찾고 호모그래피로 mm 환산)

교정은 **눈으로 검증**했습니다 — `calibrate check`가 투영한 레일·팔레트·원판을 배경
이미지에 겹쳐 그립니다. 독립 검증으로, front 교정에서 복원한 카메라 자세가
**"높이 2.43 m, 팔레트 안쪽 끝에서 1.4 m"** 로 물리적으로 타당하게 나왔습니다.

### 3.3 차량 추정

Hailo bbox는 쓰지 않습니다(확정안대로 ROI 용도로만 쓰기로 했고, 이 랩에서는 아예 미사용).

1. 카메라별 중앙값 배경과의 차분으로 실루엣
2. 주차기 영역(팔레트 사각형 투영 + 차체 높이만큼 확장) 밖은 버림 — 문이 열리면 바깥이 보임
3. 실루엣의 **아래쪽 경계 = 타이어 접지선**으로 보고 지면 호모그래피로 월드(mm)에 올림
4. 접지점들에서 팔레트 축에 정렬된 사각형을 백분위수로 강건하게 추출
5. 자세 복원이 믿을 만하면 실루엣 최상단으로 높이까지 → 직육면체

### 3.4 출력

- 주석 이미지: 팔레트(분홍)·레일(노랑)·판정 영역(회색), 차량 바닥 사각형(연두),
  진입쪽 끝(+x, 파랑)·안쪽 끝(−x, 주황)·좌우 바퀴선(노랑), 실루엣 외곽선(청록),
  길이·폭 치수 화살표, 우상단 측정값 패널.
- 실패 시: **빨간 테두리 + 좌상단 한국어 실패 사유**.
- `out/report.html`: 요약·읽는 법·지면 교정 근거·전체 판정 카드(필터: 판정됨/불가/카메라/스냅샷).

## 4. 검증 결과 (이미지 317장)

측정 대상 173장(교정된 카메라 + 스냅샷) 중 **18장 판정 성공**.
추정 길이 2,742 ~ 4,164 mm, 폭 1,279 ~ 2,578 mm.

### 되는 것

- 지면 교정이 실물과 맞는다 (투영한 레일·팔레트가 실제 위에 얹힘).
- **Hailo 없이 CPU 배경차분만으로 차량 실루엣이 잡힌다.**
- 사선 카메라 스냅샷에서 **바닥 사각형·앞뒤 끝·바퀴선·치수**가 나온다.

### 안 되는 것과 그 원인 (전부 규명됨)

1. **3D 직육면체는 아직 못 그린다 — 바닥 사각형까지.**
   `opposite_side`는 호모그래피에서 복원한 카메라 자세가 지면과 **16 %** 어긋난다.
   4점 호모그래피 + 어안 왜곡 때문에 "정사각 화소 핀홀" 가정이 성립하지 않는다.
   → **체커보드 내부 파라미터 측정이 실제로 필요하다는 것이 수치로 확인됨.**
   `front`는 자세가 0.17 %로 잘 맞지만 아래 2번 때문에 차량 접지선을 못 본다.
2. **전면 카메라는 지면이 진입부 약 1.5 m만 보인다.** 카메라가 2.4 m 높이에 있고
   아래쪽 화각 한계 때문에 4 m 이내 바닥이 안 보인다. 즉 **주차 완료된 차량의 타이어
   접지선을 전면 카메라로는 볼 수 없다.** 전면은 번호판·좌우 치우침 보조용이고,
   길이·위치는 사선 카메라가 맡아야 한다. (확정안의 "전면은 보조·교차 검증" 판단이 맞았다)
3. **증거 클립(stream2)과 스냅샷(stream1)의 화각이 다르다.** 같은 카메라인데 크롭이 달라
   같은 지면 교정을 쓸 수 없다. 지금은 클립 프레임을 "측정 보류"로 표시한다.
   → 클립으로 측정하려면 stream2 전용 교정이 따로 필요하다.
4. **사선 카메라 한 대로는 폭이 부정확하다.** 먼 쪽 바퀴가 안 보여 접지선의 y 범위가
   차체 폭이 아니다. 폭은 전면 또는 반대편 사선과 교차해야 한다.
5. `rear_side` 미교정.
6. 길이가 실제보다 짧게/길게 나오는 개체가 있다. 실루엣 아래 경계가 타이어 접지선이
   아니라 그림자·록커패널을 따라가는 경우가 섞인다.

### 구현하며 알게 된 실무 사항

- **흰 차 + 회색 바닥은 명도 차이가 거의 없다.** 그레이스케일 배경차분은 차체를 거의 못
  잡는다. **Lab 색공간 거리 + 채널별 조명 보정**으로 바꾸고 나서야 잡혔다.
- 중앙값 배경은 표본이 적으면(16~23장) 차량 잔상이 남아 차분을 망친다. 카메라당
  80~90장으로 늘리자 빈 주차기 배경이 깨끗해졌다.
- 차량 증거 스냅샷은 **5초 프리롤 시점**이라 차가 아직 바깥에 있는 경우가 많다.
  클립 프레임은 **클립 전체에 고르게 퍼뜨려** 뽑아야 진입한 장면이 들어온다.
